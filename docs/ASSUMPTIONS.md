# Assumptions

> The scenario is intentionally incomplete. Record every assumption you needed to make, and the part it affects.

| # | Assumption | Why I needed it | Part(s) affected |
|---|---|---|---|
| 1 | The planned window for `payment_event` is 13 months of **hot data**, configurable per country, and it is a **design assumption**: not a legal period, not a deletion date and not a guarantee. No purge runs while the detailed archive does not exist, so older rows stay stored and stay queryable; live data grows ≈1.6 GB/month until the archive exists. | No legal retention period exists in the material, and the design still has to size storage and answer FR7 over a defined horizon. | `docs/design/SOLUTION_DESIGN.md` §5.1, §6.4, §7; storage sizing in `ADR-0002` |
| 2 | Five years is a **provisional planning baseline only** — never a compliance statement for MX, CO or CL and never a legal maximum. | NFR6 defers to each country's law; a planning number is needed for estimates before Compliance rules. | A2, A6 |
| 3 | Applicable retention is **country- and record-category-specific statutory/contractual retention, subject to compliance validation**. The design records no per-country legal figure, because the researched periods are category minimums and cannot be stated as ceilings. | The design must not assert a legal conclusion it cannot source, and a minimum quoted as a maximum would become an unverified legal claim in the deliverable. | A2 |
| 4 | The raw provider payload is **not stored today**; keeping it is an open privacy/evidence decision, and no 30-day rule has been adopted. | `payload_hash` lets a known body be checked against a hash without storing payer data, but it neither reconstructs the original body nor serves as evidence by itself, and dispute investigation may need that body. | §3.1, §5.1, A2 |
| 5 | Salesforce holds the **last applied payment state** per payment, not the event history. | `Premium_Payment__c` is upserted on `Payment_Key__c`; no per-event record exists there, so event history lives only in the operational store. | §5, §5.1, §7 |
| 6 | The **data store and the stack are decided and accepted in `ADR-0002`** (`Accepted`, amended 2026-11-21 for canonical-event publication). | Part B and Part C build on it, and its status is reviewable evidence. | `ADR-0002`, Part B, Part C |
| 7 | The canonical event is a **valid, accepted and deduplicated notification** carrying the provider's reported state; it is not proof that Salesforce applied it, and a broker ack is not consumer processing. Publication is at-least-once; consumers deduplicate on `(provider, event_id)` and order by `status_changed_at`. | FR6 requires publication but the material does not define what "published" proves; without this, consumers could read the event as a Salesforce confirmation. | `docs/design/SOLUTION_DESIGN.md` §3.3, §4.1; `ADR-0002` amendment |
| 8 | The canonical event carries **`refunded_amount_minor`** (nullable, same currency and minor unit as `amount_minor`), **`refunded_amount_semantics`** (`PROVIDER_REPORTED_UNSPECIFIED` when the amount is present) and **`refund_scope`** (`FULL` / `PARTIAL` / `UNKNOWN`, `null` unless `REFUNDED`). Quetzal reports `amount_refunded` but does not document whether successive refunds are cumulative, so it is carried as reported and never summed; `FULL`/`PARTIAL` only compare that reported amount with the charge amount in the same event, never a historical total. Andina and Austral report no refunded amount and no extent, so `UNKNOWN` with a null amount; their payment-level reversal still maps to `Refunded` in Salesforce and `UNKNOWN` is not treated as `PARTIAL`. The Salesforce write is withheld only for `PARTIAL` (ADR-0001 definition 3 unchanged). | The event must not assert a total refund, a cumulative figure or a `0` the provider never reported; a payment-level reversal must not become an automatic partial-refund hold. | `docs/design/SOLUTION_DESIGN.md` §3.1–§3.3, §5 |
| 9 | `MessageId` is a stable function of `(provider, event_id)`: `provider:event_id` when at most 128 characters, SHA-256 otherwise. Publication is at-least-once; broker duplicate detection is an optimisation, not a guarantee. | Service Bus needs a message id, and the provider event id is only unique inside one provider. | `docs/design/SOLUTION_DESIGN.md` §4.1; `ADR-0002` amendment |
| 10 | The **volume and write model**: 15,000 notifications/day on normal days, 120,000 on four month-end days, 3% duplicates, 1.1 accepted events per payment, three inserts + one `payment_state` upsert + four outbox updates per event (claim and completion on each of the two destination rows). That gives ≈876,600 notifications, ≈850,300 unique events, ≈6.8 M row writes and ≈1.6 GB/month; 13 months ≈20.7 GB live / ≈26.9 GB with 30% overhead. It is an estimate, not a benchmark, and it does not prove B1MS capacity. | NFR1 gives volumes but not a write model; the previous 1 GB/month figure assumed every day was a peak day and ignored the second outbox row and the updates. | `docs/design/SOLUTION_DESIGN.md` §5, §6; `ADR-0002` §Cost basis |
| 11 | **Service Bus Premium** is the private-network target. The budget uses one messaging unit as a starting configuration and treats its price as an order-of-magnitude allowance, not a verified subscription quote. | Private Link changes the viable tier and cost; capacity, regional pricing and any discount need validation before an authorized rollout. | `ADR-0002` §Cost basis; Part C |
| 12 | **Planning row sizes and overhead**: `payment_event` 700 B/row, `outbox` 450 B/row, `payment_state` 300 B/row, each including data and indexes, plus a **30% overhead** for WAL, index bloat and the backup working set. They are sizing assumptions, not measurements and not requirements, and the 13-month figures (≈20.7 GB live, ≈26.9 GB with overhead) inherit them. | The material gives volumes but no row sizes or overhead figure, and storage still has to be provisioned from something; a measured value would need a load test that has not been run. | `docs/design/SOLUTION_DESIGN.md` §6.4; `ADR-0002` §Cost basis |
| 13 | Equal provider timestamps are ordered `REFUNDED > CAPTURED > FAILED > PENDING`, then by event ID for a deterministic winner. This conservative default is subject to agreement with product and each provider; the ID is not evidence of chronological order. | Provider clocks can tie and arrival order cannot safely decide whether to undo a refund. | Part A, local V9 migration and relay |
| 14 | The local operations console uses the existing country-scoped API and a disposable local token issuer. Production authentication, operator approval and reconciliation are separate; no queue action in the demo contacts a production destination. | Demonstrate the operator workflow without a second backend, a browser stack or a real identity provider. | FR7 and optional product extension |
| 15 | The 30-second local Salesforce call reservation assumes a production adapter enforces a shorter request deadline. Neither that reservation nor a database claim token establishes remote write outcomes. | Database capacity can recover after client loss without treating an ambiguous remote payment as safe to retry. | Part A, local relay, Part D |
